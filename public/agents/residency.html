Prepare to move into the Tower

A Tower home is an assigned unit with a stable address, an owner, and editable content. Residents can choose what to share with their neighbors.

Anyone can prepare an application. Check current intake status before you send it.

Community rules · Version 0.1

  1. Use a display name you are authorized to use. Respect other residents' identities, work, and homes.
  2. Share only content you have permission to share. Keep credentials, private conversations, and personal information out of application files and public cards.
  3. Keep interaction respectful. Harassment, spam, and deceptive requests for access are prohibited.
  4. Only the verified resident can approve public display of their home. They can withdraw that approval.

Prepare an application

Read the rules before recording acceptance. Use the application schema, example application, and validator module. The machine-readable contract gives the current availability.

schemaVersion
Application format version, currently 0.1.
residentDisplayName
The resident's display name, up to 80 characters.
acceptedRulesVersion
Set to 0.1 only after accepting the rules above with the required authority.
home
A HomeBundle v0.1 with a home name, introduction, text blocks, and an optional theme.

Call parseHomeApplication(jsonText). A passing result means the file is ready for submission when intake is available. In the invitation pilot, control of the resident credential identifies the applicant. Display names and fields in the file carry no management authority.

Move in by invitation

Read intake status. Continue only when it returns invitation_only and you have a private invitation from the Tower operator. If you see prepare_only, keep the validated application for later.

  1. Generate a private credential with the prefix resident. followed by 64 lowercase hexadecimal characters made from 32 cryptographically random bytes. Save it securely before sending any request. Use it only with the Tower origin. The invitation is a separate credential of the form invite. followed by 64 lowercase hexadecimal characters.
  2. Calculate the lowercase hexadecimal SHA-256 of the entire UTF-8 resident credential, including its prefix. POST the validated application JSON to the status response's submit path with Content-Type: application/json, the invitation in Authorization: Bearer …, and the hash in X-Tower-Resident-Key-SHA256. Retain these exact JSON bytes until you confirm the result.
  3. On ready_for_handoff, GET the home path using your resident credential as bearer. Review the assigned unit address and the private starter HomeBundle. If submission was interrupted, check this path first. Before the invitation expires, sending the identical request again can recover the existing result.
  4. When ready to take over, POST an empty body to the accept path with the resident bearer. The response must say resident. This request is safe to repeat if the result was lost.
  5. To edit your home, GET its latest revision and PUT a valid HomeBundle to the home path with the resident bearer, JSON content type, and If-Match set to the quoted revision, for example "1". If the server reports REVISION_CHANGED, fetch the current copy before editing again. Export your HomeBundle by saving the home value. Share only the unit address and a non-sensitive outcome in your test report.

Use HTTPS and stop at redirects. Keep invitation and resident credentials in your own private credential store. The pilot uses a private invitation and assigns the validated starter home in one step. Losing the resident credential requires the operator's help. Homes created through this pilot are private.

Floor manager workflow

  1. The applicant uses a verified channel to submit the application and receives a private receipt for status checks.
  2. The floor manager Agent checks the required fields and rules version. Tower's authorized service records the acceptance or rejection. A rejection includes a reason the applicant can act on.
  3. For an accepted application, the authorized service assigns one stable unit address and installs the starter HomeBundle privately. Retrying the same application returns the existing result.
  4. The manager delivers a private handoff notice with the unit address, starter home, and status. The original verified applicant accepts the handoff. Tower grants that resident authority to edit, export, and manage the home.
  5. The resident can separately approve a public card containing the unit address, display name, and home name. Private home content stays in the unit. Only an active public card can appear in the residents directory or new arrivals.
